# SePlatform Deploy Tool — Linux

Инструмент установки, обновления и удаления **`.deb`-компонентов SePlatform**
на Linux-машинах. Это Linux-аналог Windows-инструмента `Deploy.ps1` (MSI →
`.deb`, службы Windows → systemd, реестр → `dpkg`).

В состав входят два скрипта:

1. **`Deploy.sh`** — установка / обновление / удаление `.deb`-компонентов
   по whitelist (`manifest-linux.json`) из ZIP-архива или папки с `.deb`.
2. **`ServerCopies.sh`** — управление **дополнительными копиями**
   SePlatform.Data Server (несколько экземпляров на одной машине).

> Windows-версия (`Deploy.ps1` + `modules/`, MSI-архив) работает только на
> Windows. На Linux компоненты поставляются в виде `.deb`-пакетов, а для
> сервера данных дополнительно доступен `ServerCopies.sh`.

---

## 1. Deploy.sh — установка/обновление/удаление .deb

### Назначение

Скрипт по белому списку (`manifest-linux.json`) находит в источнике (ZIP или
папка с `.deb`) файл для каждого компонента, сравнивает версию пакета с
установленной (`dpkg`), останавливает соответствующие службы/процессы и
устанавливает (`dpkg -i`) либо удаляет (`dpkg -r`) пакеты. По ходу пишется
отчёт `report.json` в каталог сессии.

Возможные статусы компонентов:

| Статус       | Значение |
|--------------|----------|
| `UPDATE`     | установлен старый, в источнике есть новее — будет обновлён |
| `INSTALL`    | будет установлен (выбран пользователем) |
| `MISSING`    | не установлен, кандидат есть (в режиме install/update) |
| `OK`         | установлен, версия совпадает с кандидатом |
| `SKIP_NEWER` | установлена версия новее, чем в источнике |
| `NO_DEB`     | подходящего `.deb` в источнике нет |
| `BLOCKED`    | не пройдены обязательные зависимости (например, DevStudio) |
| `UNINSTALLED`| пакет удалён |
| `ERROR`      | ошибка установки/удаления или проверки |

### Требования

- Debian-совместимый дистрибутив (там, где есть `dpkg`); желательно с systemd
  для управления службами;
- права **root** (`dpkg -i`, systemctl);
- `bash`, `dpkg`, `dpkg-query`, `dpkg-deb`, `unzip` (если источник — ZIP),
  `python3` **версии 3.x** (для парсинга манифеста и отчёта `report.json`;
  скрипт проверяет версию при запуске; `jq` — необязательный
  запасной вариант для простых полей конфигурации);
- веб-компоненты HMI (`*WebViewer`) дополнительно зависят от **Python 3**
  (блокирующая зависимость в манифесте — без него статус `BLOCKED`);
- `timeout` (из `coreutils`), `pgrep` — для остановки процессов;
- для **DevStudio** на Linux дополнительно должны быть установлены
  `dotnet-runtime-8.0`, `libgdiplus`, `subversion` (SVN) — без них пакет
  заблокирован статусом `BLOCKED`.

> `Tools` и `Documentation` в Linux-версии не управляются: для них
> поставляются только Windows-сборки (MSI/ZIP), `.deb` нет.

### Запуск

```bash
sudo bash Deploy.sh -a "/path/to/HMI 2.0.38.zip"
# или папка с .deb:
sudo bash Deploy.sh -a /path/to/deb_folder
```

Без параметров скрипт запускается в интерактивном режиме: мастер предложит
выбрать сценарий (установка/обновление, копии сервера), путь к архиву
(или возьмёт `defaultArchive` из конфига), компоненты и запросит
подтверждение.

### Параметры

| Параметр | Описание |
|----------|----------|
| `-a, --archive PATH`  | Источник: ZIP-архив или папка с `*.deb` (обязателен в неинтерактивном режиме) |
| `-c, --config PATH`   | Файл конфигурации (по умолчанию `config-linux.json`) |
| `-m, --manifest PATH` | Файл манифеста/whitelist (по умолчанию `manifest-linux.json`) |
| `-L, --log-path DIR`  | Корневой каталог логов (по умолчанию из конфига: `/var/log/SePlatform/Deployment`) |
| `-l, --locale LOC`    | Предпочтение локали, например `ru_RU` или `en_US` |
| `-n, --dry-run`       | Сухой прогон: показать план и отчёт, ничего не менять |
| `-y, --auto-approve`  | Не запрашивать подтверждение |
| `-q, --non-interactive` | Без интерактивных запросов |
| `-u, --update-only`   | Обновлять только установленные компоненты (MISSING пропускаются) |
| `-U, --uninstall`     | Режим удаления установленных компонентов |
| `-s, --server-copies` | Запустить `ServerCopies.sh` (копии Data Server) |
| `-k, --keep-temp`     | Не удалять временную папку с распакованными `.deb` |
| `-h, --help`          | Справка |

Примеры:

```bash
# сухой прогон плана для ZIP-архива
sudo bash Deploy.sh -a "/mnt/share/HMI 2.0.38.zip" -n

# неинтерактивное обновление только установленных
sudo bash Deploy.sh -a "/mnt/share/HMI 2.0.38.zip" -y -q -u

# удаление установленных компонентов
sudo bash Deploy.sh -a "/mnt/share/HMI 2.0.38.zip" -U -y -q

# управление копиями Data Server
sudo bash Deploy.sh -s
```

### Коды выхода

| Код | Значение |
|-----|----------|
| 0 | Успех |
| 1 | Завершено с ошибками компонентов |
| 2 | Отменено пользователем |
| 3 | Критические зависимости/предусловия не выполнены |
| 4 | Ошибка параметров или конфигурации |

### Как это работает

1. Загрузка конфигурации `config-linux.json` (пути логов/temp, локаль,
   приоритет архитектуры, таймауты, политики).
2. Определение типа источника (`zip` или `dir`) и сбор списка `*.deb`.
3. Загрузка whitelist из `manifest-linux.json` (~30 компонентов).
4. Для каждого компонента:
   - выбор кандидата `.deb` по `debPattern` с учётом предпочтения локали
     (`ru_RU → ru → en_US → en`) и архитектуры (`amd64/x86_64 → all/any`);
   - распаковка/чтение управляющих полей (`dpkg-deb -f`: Package, Version,
     Architecture);
   - инвентаризация установленного (`dpkg-query`), сравнение версий через
     `dpkg --compare-versions`;
   - проверка зависимостей из манифеста (`blocking` зависимость, например
     `dotnet-runtime-8.0` для DevStudio) — при невыполнении статус `BLOCKED`.
5. Показ плана изменений, выбор компонентов (или `-y`/`-q` — все).
6. Выполнение по порядку `order` из манифеста:
   - перед обновлением/удалением останавливаются службы
     (`systemctl stop`) и матчинговые процессы (`pgrep` + `kill`);
   - **переименование пакета**: если установленный пакет называется иначе,
     чем пакет в `.deb` (например, `seplatform.hmi.charts-desktop` →
     `seplatform.hmi.charts-desktop_ru_ru` в локализованных сборках), старый
     пакет сначала снимается (`dpkg -r`, конфиги сохраняются), а новый
     ставится с `--force-confdef`; при конфликте файлов с посторонним
     пакетом выполняется один повтор с `--force-overwrite`;
   - установка: `dpkg -i <файл>` (или `apt-get install -y ./файл`, если
     `installWithApt=1`), затем проверка `dpkg-query` по `packagePattern`;
   - удаление: `dpkg -r <пакет>` (или `dpkg -P`, если `purgeOnUninstall=1`);
   - службы запускаются обратно (`systemctl start`), если юнит существует.
7. Отчёт в каталог сессии: `Deployment.log` (общий лог) и `report.json`
   (структурированный, с полями компонентов и счётчиками). В `error`
   попадает реальная причина сбоя из вывода dpkg, а не только код возврата.

Каждая операция ограничена таймаутом (`installTimeoutSeconds`,
`uninstallTimeoutSeconds`); по превышении — статус `ERROR` и переход к
следующему компоненту (`continueOnComponentError`).

### Предупреждение о недостающих компонентах

После построения плана считаются компоненты со статусом `MISSING`,
`NO_DEB` и `BLOCKED`. Если их больше, чем `missingWarnThreshold`
(по умолчанию 3), выводится выделенный блок `!! ВНИМАНИЕ: НЕ УСТАНОВЛЕНО
N КОМПОНЕНТОВ !!` со списком и причиной по каждому (для `BLOCKED` — имя
недостающей зависимости), в `Deployment.log` пишется строка `NOT INSTALLED`,
а в интерактивном режиме вопрос подтверждения меняется на
`Continue (WARNING: N components are NOT installed)`. В итоговой сводке
добавляется строка `Not installed at start`.

### Файлы конфигурации

`config-linux.json` (плоский JSON):

| Ключ | Назначение |
|------|------------|
| `logRoot` | Корневой каталог сессий (по умолчанию `/var/log/SePlatform/Deployment`) |
| `tempRoot` | Временная папка для распаковки `.deb` (по умолчанию `/tmp/SePlatform-Deploy`) |
| `defaultArchive` | Путь к источнику по умолчанию (используется в интерактивном мастере) |
| `localePreference` | Приоритет локалей: `["ru_RU","ru","en_US","en"]` |
| `preferArch` | Приоритет архитектур: `["amd64","x86_64","all","any"]` |
| `installTimeoutSeconds` / `uninstallTimeoutSeconds` | Таймауты операций dpkg |
| `keepTempOnError` | Не удалять временную папку при ошибках |
| `cleanupTempOnSuccess` | Удалять временную папку после успеха |
| `warnOnNewerVersion` | Предупреждать, если установлена версия новее архивной |
| `continueOnComponentError` | Продолжать после ошибки компонента |
| `requireRoot` | Требовать права root |
| `installWithApt` | Ставить через `apt-get install -y ./файл` вместо `dpkg -i` |
| `purgeOnUninstall` | Удалять через `dpkg -P` вместо `dpkg -r` |
| `missingWarnThreshold` | Порог (по умолчанию 3) количества неустановленных компонентов, начиная с которого выводится громкое предупреждение |

`manifest-linux.json` — список компонентов (id, displayName, group, required,
`debPattern` — glob по имени файла, `packagePattern` — regex по имени пакета
в dpkg, `localePreference`, `archCode`, `order`, `services`/`processes` для
остановки перед обновлением, `dependencies`). Заполнен по фактическим
`.deb`-пакетам (в том числе пакеты с суффиксом локали вида
`seplatform.hmi.charts-desktop_ru_ru` и смешанными регистрами
`SePlatform.Domain`, `SePlatform.Security`).

### Где сессия и отчёт

```
/var/log/SePlatform/Deployment/<YYYY-MM-DD_HH-MM-SS>/
  Deployment.log     — общий лог сессии
  components.tsv     — строки компонентов (\x1f-разделённые)
  report.json        — отчёт: session, counters, exitCode, result, components[]
```

Пример `report.json`:

```json
{
  "session": { "startTime": "...", "endTime": "...", "mode": "UPDATE",
               "sourceType": "zip", "dryRun": false, ... },
  "counters": { "CountUpdated": 0, "CountInstalled": 0, ... },
  "exitCode": 0,
  "result": "SUCCESS",
  "components": [
    { "id": "HMI.Alarms", "displayName": "SePlatform.HMI.Alarms",
      "status": "OK", "package": "seplatform.hmi.alarms",
      "oldVersion": "3.9.2", "newVersion": "3.9.3+b1.r13758",
      "installFile": "seplatform.hmi.alarms-ru_RU-....deb",
      "installExitCode": "0", "verified": true, "error": "" }
  ]
}
```

### Примечания по Linux

- Идентификатор экземпляра Data Server на Linux хранится в
  `/opt/SePlatform/SePlatform.Server/SePlatform.Server.json`
  (`Instance.Id`; старый формат — `SePlatform.Server.xml`).
- Имена systemd-юнитов выбираются по соглашению из имени пакета и при
  необходимости правятся в `manifest-linux.json` (поле `services`).
- Скрипт проверяет наличие юнита перед `systemctl start/stop` — отсутствующие
  службы не вызывают ошибок.

## 2. ServerCopies.sh — дополнительные копии Data Server

Bash-инструмент для управления **дополнительными копиями SePlatform.Data Server**
на Linux-машинах с systemd. Основная служба ставится `.deb`-пакетом
(через `Deploy.sh`), а этот скрипт обслуживает только дополнительные
копии (экземпляры) сервера данных.

### Назначение

На одной машине может работать несколько экземпляров SePlatform.Data Server:
основная служба (ставится `.deb`-пакетом, каталог `SePlatform.Server`) и
дополнительные копии (`SePlatform.Server<N>`), которые можно:

- создавать (копировать основную установку в новую папку с новыми службой/портом/ID);
- обновлять (синхронизировать бинарники из основной установки);
- удалять (снять службу и удалить каталог).

Каждая копия — это отдельный каталог с собственным конфигом
(`SePlatform.Server.xml` и/или `SePlatform.Server.json`) и отдельным
systemd-юнитом.

### Как это работает

1. Скрипт сканирует `SERVER_ROOT` (по умолчанию `/opt/SePlatform`) и находит
   каталоги по имени `SePlatform.Server*`, наличию исполняемого файла
   `SePlatform.Server` и конфига `SePlatform.Server.xml`.
2. Из конфигурации каждой копии читается:
   - имя службы — атрибут `ServiceName` элемента `install` в XML;
   - порт — атрибут `Port` элемента `Connection` в XML;
   - идентификатор экземпляра — `Instance.Id` из `SePlatform.Server.json`
     (новые версии) либо `Instance.ID` из XML (старые версии);
   - состояние службы — через `systemctl is-active`.
3. Каталог, совпадающий с `MAIN_FOLDER` (`SePlatform.Server`), считается
   **основной службой** — её нельзя удалить или пересоздать этим инструментом.
4. Выводится меню операций (см. ниже).

### Именование юнитов

Имя systemd-юнита формируется из имени службы в нижнем регистре с суффиксом
`.service` (например, служба `seplatform.server1` → `seplatform.server1.service`).
Юниты лежат в `UNIT_DIR` (по умолчанию `/lib/systemd/system`).

### Требования

- Linux с **systemd** (Debian/Ubuntu/RHEL — подойдёт любой, где есть `systemctl`);
- права **root** (запись в `/lib/systemd/system`, `systemctl`, `daemon-reload`);
- установленный основной SePlatform.Data Server (`SePlatform.Server`), из
  которого копии создаются и обновляются;
- для обновления копий желателен `rsync` (если его нет — используется
  `tar` как запасной механизм синхронизации);
- `grep`/`sed` с поддержкой `-P` (PCRE) и `-E` (GNU-версии, идут в составе
  стандартного набора утилит).

### Запуск

```bash
sudo bash ServerCopies.sh
```

Или, сделав скрипт исполняемым:

```bash
chmod +x ServerCopies.sh
sudo ./ServerCopies.sh
```

Без прав root и без `systemd` скрипт завершится с ошибкой.

### Меню

```
SePlatform.Data Server copies (detected):

  [1] SePlatform.Server (MAIN)  service=seplatform.server  port=4573  [active]
        (main server)
  [2] SePlatform.Server1 (COPY)  service=seplatform.server1  port=4574  [active]

SePlatform.Data Server copies menu:
  [1] Install a new additional copy (initial installation)
  [2] Update additional copies from the main server
  [3] Remove an additional copy
  [4] Rescan detected copies
  [5] Exit
```

Пункты меню:

- **1 — Установить новую копию**: копирует каталог основной службы в новую
  папку и регистрирует её как отдельную службу.
- **2 — Обновить копии**: синхронизирует бинарники из основной установки в
  выбранные копии (конфиги копий не перезаписываются), перерегистрирует и
  запускает службы.
- **3 — Удалить копии**: снимает службу копии и удаляет её каталог.
- **4 — Обнаружить заново**: повторное сканирование `SERVER_ROOT`.
- **5 — Выход**.

Выбор копий списком: `A` — все, `N` — ничего, `1,2 4` / `1 3` — конкретные номера
(разделители — запятая, точка с запятой, пробел). Любая операция, меняющая систему,
защищена подтверждением `[Y/N]`.

### Операции

#### Установка новой копии [1]

Требуется установленная основная служба. Скрипт запрашивает:

- **имя папки** (по умолчанию `SePlatform.Server<N>`, где `N` — следующий
  свободный номер);
- **имя службы** (по умолчанию — имя папки);
- **TCP-порт** (по умолчанию — первый свободный, начиная с 4573);
- идентификатор экземпляра генерируется автоматически (UUID в верхнем регистре).

Далее скрипт:

1. проверяет уникальность имени службы, порта и ID среди обнаруженных копий;
2. копирует каталог основной службы в новую папку (`cp -R`);
3. переписывает в `SePlatform.Server.xml` копии `install.ServiceName`,
   `Connection.Port` и `Instance.ID`;
4. записывает новый ID экземпляра в `SePlatform.Server.json`
   (файл создаётся при необходимости);
5. создаёт systemd-юнит: копирует юнит основной службы и правки
   `Description`, `WorkingDirectory`, `Environment=LD_LIBRARY_PATH`,
   `ExecStart=.../<имя_папки>/SePlatform.Server`;
6. выполняет `systemctl daemon-reload`, `enable`, `start`.

Конфликт имени службы/порта/ID прерывает установку.

#### Обновление копий [2]

Синхронизирует бинарники из основной установки в выбранные копии:

- выбранные службы копий временно останавливаются (служба основной — не трогается);
- бинарники копируются `rsync -a --delete` (или через `tar`), при этом
  `SePlatform.Server.xml` и `SePlatform.Server.json` копии **не перезаписываются**;
- если основная установка использует новый формат конфига (есть
  `SePlatform.Server.json`), ID экземпляра копии переносится из XML в JSON
  (`Instance.Id`), а старый `Instance.ID` в XML **комментируется** (не удаляется);
- копия перерегистрируется и запускается обратно.

#### Удаление копий [3]

Выбранные копии:

- останавливаются и отключаются (`systemctl stop`, `disable`);
- unit-файл удаляется из `UNIT_DIR`;
- каталог копии удаляется (`rm -rf`);
- в конце `systemctl daemon-reload`.

Основная служба в списке на удаление отсутствует.

### Защита и ограничения

- **Основную службу нельзя удалить или пересоздать** этим скриптом — только
  копии `SePlatform.Server<N>`.
- Действия над службой (`stop`, удаление unit-файла) выполняются **только если**
  `ExecStart` её юнита указывает на каталог именно этой копии
  (проверка `unit_belongs_to`). Это исключает случайное отключение чужой или
  основной службы.
- Если у копии остался только каталог без корректной привязки службы
  (например, после прерванной установки), служба не останавливается и не
  удаляется — удаляется лишь сам каталог.
- Имя службы, порт и идентификатор экземпляра проверяются на уникальность
  при создании копии.
- Конфигурационные файлы копии (`*.xml`, `*.json`) не удаляются и не
  перезаписываются при обновлении.
- Работа только с каталогами вида `$SERVER_ROOT/$MAIN_FOLDER*`; каталоги без
  исполняемого файла сервера и конфига игнорируются.

### Конфигурация

Настройки задаются переменными окружения (до запуска скрипта):

| Переменная    | Значение по умолчанию | Описание |
|---------------|-----------------------|----------|
| `SERVER_ROOT` | `/opt/SePlatform`     | Каталог, где лежат каталоги серверов |
| `MAIN_FOLDER` | `SePlatform.Server`   | Имя каталога основной службы |
| `EXE_NAME`    | `SePlatform.Server`   | Исполняемый файл сервера |
| `XML_NAME`    | `SePlatform.Server.xml` | Файл конфигурации (XML) |
| `JSON_NAME`   | `SePlatform.Server.json` | Файл конфигурации экземпляра нового формата |
| `UNIT_DIR`    | `/lib/systemd/system` | Каталог systemd-юнитов |

Пример:

```bash
SERVER_ROOT=/opt/SePlatform \
MAIN_FOLDER=SePlatform.Server \
UNIT_DIR=/etc/systemd/system \
sudo -E bash ServerCopies.sh
```

> Внимание: `systemd` в разных дистрибутивах может использовать
> `/usr/lib/systemd/system` вместо `/lib/systemd/system`. При необходимости
> укажите `UNIT_DIR` явно.

### Проверка результата

После любой операции перезапустите скрипт (или выберите пункт «Rescan») —
список копий обновится. Состояние служб контролируется штатно:

```bash
systemctl status seplatform.server1
systemctl list-units 'seplatform*'
```

### Пример полного цикла

```bash
# 1. Обновить основной сервер и компоненты из архива (.deb)
sudo bash Deploy.sh -a "/mnt/share/HMI 2.0.38.zip"

# 2. Обнаружить установленные копии
sudo ./ServerCopies.sh

# 3. Создать дополнительную копию: пункт [1]
#    folder = SePlatform.Server1, service = seplatform.server1, port = 4574

# 4. После обновления основного сервера (.deb) — обновить копии: пункт [2]

# 5. Удалить копию, когда она больше не нужна: пункт [3]
```

### Ограничения

- Скрипт **не устанавливает и не обновляет основную службу** — она управляется
  штатным `.deb`-пакетом. Этот скрипт лишь копирует/синхронизирует её бинарники.
- Обновление копий работает «из основной установки в копии»: сначала должен
  быть обновлён основной сервер.
- Скрипт рассчитан на интерактивную работу; для неинтерактивного сценария
  предлагайте значения по умолчанию (клавиша Enter).
- Механизм синхронизации `--delete` (rsync) удаляет в копии файлы, которых нет
  в основной установке, кроме конфигов `*.xml`/`*.json`.
